### BUG server-001
- **Severity:** high
- **File:** `server/server.js:1317-1336`
- **Title:** `race:fix` forwards client-supplied `ts` verbatim with no `Number.isFinite` check
- **Repro:** Two nearby riders in a running race. Attacker sends `{"t":"race:fix","lng":..,"lat":..,"ts":"NotANumber"}` — payload with `ts:"NotANumber"` is relayed to all members.

- **Repro:** Trigger a bot reply whose `B.pick` or `JSON.stringify` throws (e.g. malformed bot config).
- **Impact:** Process crash (only saved by the global handler).

### BUG server-003
- **Severity:** critical
- **File:** `server/server.js:896, 1747-1751`
- **Title:** `hello` with token sets `online.set(u.id, c)` but never terminates the prior socket — zombie connection leaks, double rider pin
- **Repro:** Sign in on tab A, then tab B as the same user. Both stay connected; both in `clients`; other riders see two pins for one account.

### BUG server-004

- **Impact:** Data loss — recent account/race/profile writes lost on shutdown.

### BUG server-005

### BUG server-008
- **Severity:** critical
- **File:** `server/server.js:1703` (and all `rateOk('...:'+c.ip)` sites)
- **Title:** `c.ip` is derived from `x-forwarded-for` unconditionally → spoofable → all per-IP rate limits and the per-IP connection ceiling are defeated
- **Repro:** `curl -H "X-Forwarded-For: 1.2.3.4" ...` per request; each is a "new IP". Open 1000 sockets with unique spoofed XFF — all pass `MAX_PER_IP`.

- **Fix:** Only trust `x-forwarded-for` when `req.socket.remoteAddress` is in a configurable trusted-proxy list; else use `req.socket.remoteAddress`.

- **Fix:** In `readBody`'s `'data'` handler, call `json(res, 413, {error:'Request too large'})` directly when the cap is exceeded (then `req.destroy()`); don't rely on the `'end'` cb that never fires after destroy.

### BUG runtime-004
- **Severity:** medium
- **File:** `server/server.js:221-251` (specifically 231, 233, 250)
- **Title:** A valid JSON body of `null` is misreported as `413 "Request too large"` (sentinel collision in `readBody`)
- **Repro:** `POST /api/profile` with body `null` (4 bytes) → `413 {"error":"Request too large"}`. (Numeric `5` / string `"x"` / `true` correctly return 400.)
- **Expected:** `400 {"error":"Bad request"}`.
- **Fix:** Use distinct sentinels for oversized vs socket-error vs the legitimate value `null`, or have `readBody` emit the 413/400 response itself.

### BUG runtime-005
- **Severity:** medium
- **File:** `server/server.js:399-408` (specifically 403-406)
- **Title:** `/api/route` returns `502 "Routing service unavailable"` for client-side input errors (missing/invalid `from`/`to`) instead of 400
- **Repro:** `POST /api/route {}` / `{from:[999,37.7],...}` / `{from:'x',...}` — all return `502 {"error":"Routing service unavailable"}`.
- **Expected:** `400 {"error":"bad coords"}` (sibling endpoints `/api/waze` and `/api/hotspots` validate correctly).
- **Fix:** Add `if (!tomtom.isLngLat(body && body.from) || !tomtom.isLngLat(body && body.to)) return json(res, 400, { error: 'bad coords' });` before calling `tomtom.route`.

### BUG runtime-006
- **Severity:** low
- **File:** `server/server.js:1590-1687` (no `requestTimeout`/`headersTimeout` override)
- **Title:** No HTTP request timeout override — a POST with `Content-Length` set but no body holds a socket for the 5-minute Node default (slowloris exposure)
- **Repro:** `POST /api/register` with `Content-Length:100`, send no body. After 8 s the server has neither responded nor closed; socket held toward `MAX_CLIENTS=200` for 5 min.
- **Expected:** Cap incomplete requests at 10–30 s.
- **Fix:** After `httpServer.listen(...)`: `httpServer.requestTimeout = 15000;` (and optionally `httpServer.headersTimeout = 12000;`).

### BUG add-002  ·  visual

### BUG add-003  ·  correctness  ·  FIXED
- **Severity:** medium
- **File:** `js/weathernow.js` (`fetchNow`)
- **Title:** Weather fetch had no timeout — a hung request left `inflight=true` forever, silently freezing all future weather updates
- **Repro:** Enable Weather now; drop the network mid-request (or a stalled TCP connection to Open-Meteo). The promise never settles, `inflight` never clears, and no later `fetchNow()` ever runs again for the session.
- **Impact:** Weather card stuck on its last value (or "…") permanently after one stalled request.
- **Fix (applied):** Wrapped the fetch in an 8 s `AbortController` deadline that clears on settle in both `.then` and `.catch`, so `inflight` always resets and updates resume.

- **Impact:** Ragged two-line readout.

### BUG perf-001  ·  performance  ·  FIXED
- **Severity:** medium
- **File:** `index.html` (all `<script>` tags)
- **Title:** ~40 local scripts loaded render-blocking and sequentially; the recent HUD additions pushed it to 41
- **Repro:** Cold-load with DevTools → Network throttled. Each `js/*.js` (and the maplibre CDN) blocked parse until fetched+executed, one after another — the 11 new HUD scripts made it worse.
- **Impact:** Slower first paint / time-to-interactive, especially on mobile links; every added module linearly grew the boot cost.
- **Fix (applied):** Added `defer` to all 41 scripts (including the maplibre CDN, kept first so its global is ready for `mapview`). They now download in parallel during parse and execute in order right before `DOMContentLoaded` (which `app.js` already waits on) — nothing is render-blocking. Also added `<link rel="preconnect">` for `cdn.jsdelivr.net`, `basemaps.cartocdn.com`, and `tiles.openfreemap.org` to warm the TLS/DNS for the first script + map tiles. Verified: map still boots, 0 failed requests, all modules initialise.

### Note — HUD event cost (checked, not a bug)
The instrument modules subscribe to `gpsfix` and `tick`. `tick` fires at `TICK_MS = 1000` (1 Hz, `js/sim.js:11`), **not** the 60 fps `requestAnimationFrame` loop, and the widgets only do cheap text/transform writes — so the added per-second work is negligible (Coordinates additionally self-throttles to 500 ms). No render-loop drag was introduced.
